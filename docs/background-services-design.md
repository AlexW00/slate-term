# Historical background-service proposal

**Superseded trust/protocol design—not implementation instructions.** The user requested one powerful API for trusted clients. The reviewed [trusted API plan](trusted-automation-api-plan.md) replaces this document's bearer token, authenticated flag, capability restrictions, own-namespace-only access and pre-ready permission gate. Current behavior is documented in [manual services](background-services.md): one shared API, public generation-bound same-user endpoints, ordinary hello and no service bearer secret. Lifecycle ownership and cleanup remain. Automatic startup, enable/disable and restart/backoff are still deferred and must not be resumed from this historical proposal.

The original bounded review and proposed roadmap below are retained as historical design evidence, not a claim that all of it shipped.

## Scope and reuse

- One optional `service` declaration per registration, independent of `source`, panel `process`, commands and scope. Reuse the bounded `PluginProcessSpec` fields (absolute executable, arguments, directory, environment, ready timeout, restart limit); no `{port}` substitution. Service-only registrations are valid. Registration alone never starts a service.
- Reuse `PluginProcess` and the existing `_plugin-worker` parent-death/process-group supervisor. Do not build a second process launcher. No HTTP listener/readiness probing, hidden web view, or synthetic pane/tab identity.
- New administrative methods: `plugins.service.start/stop/restart/enable/disable/list/status/logs`. Existing `plugins.restart/status/logs` panel/command behavior remains compatible; separate discovery makes the new lifetime unambiguous. Parameterized service controls are not picker/shortcut entries. `plugin.service.start` remains a valid contributed command ID.
- No command/service storage API in this phase. Bind the service to its own plugin settings namespace; never borrow page-instance storage. Optional storage still needs its separately approved contract.

Example addition to a manifest:

```json
{"service":{"executable":"/absolute/path/controller","arguments":[],
 "restartLimit":3,"readyTimeoutSeconds":10}}
```

## Identity, transport and credentials

Use one private UnixServer endpoint per live generation, rather than adding trusted identity fields to ordinary RPC params or changing causation metadata. The existing transport already checks same-user peer credentials, uses a private 0700 directory/socket 0600, bounds input/output and cancels owned request tasks on close.

- Host creates an app-epoch-bound service runtime ID and a fresh generation/256-bit random bearer token for every launch attempt. The endpoint handler closes over registration identity/revision, runtime ID and generation. These cannot be supplied by the caller.
- Use UnixServer's optional immutable service-credential binding, with a per-peer authenticated flag. Revoke authentication immediately on every decoded hello, BEFORE protocol/metadata/authentication validation; authenticate only after all three succeed. Malformed service requests that cannot be decoded close the peer and discard its queue. Thus an invalid repeated hello followed by a queued mutation cannot retain old authentication. Default administrative servers retain their existing handshake. Service endpoints accept only exact versioned hello fields: `protocolVersion:1`, `serviceProtocolVersion:1`, `serviceId`, `generation`, `token`. Metadata remains forbidden on hello.
- The ordinary protocol handshake alone never authenticates a service. Wrong/missing/retired credentials fail closed, with a generic error and no echo of input. A bad hello followed by a queued command cannot bypass authentication.
- Hello replies include protocol versions, app instance, service ID/generation and plugin ID, never the token. The client must verify service protocol version and exact expected app/service/generation identity before discovery or dispatch; an ordinary administrative hello response cannot establish a service session even if an older server ignores unknown hello fields. Validate the generation on every dispatch and retain a validator for asynchronous effects. Closing the endpoint or retiring its generation invalidates all sessions, including already-authenticated peers.
- Bound each endpoint to 4 peers, with a 2-second unauthenticated timeout and 2-second idle timeout when no request is active. Admit at most one long poll per generation, and none before ready. Pre-ready read/resnapshot operations must be nonblocking; web/terminal waits are not bootstrap reads. Administrative stop/disable use the separate administrative endpoint, not these slots. Keep existing message/queue/output limits and a maximum 16 active/backoff reservations. Reconnect is allowed only to the same still-live endpoint/generation; no automatic rediscovery, mutation replay or reauthentication as an administrator.
- Deliver endpoint/identity/token through the exact child environment. Strip inherited `SLATE_TERM_*` before installing host-owned values; no fake pane/tab/session. `SLATE_TERM_SOCKET` points to the service endpoint, with app instance and CLI path plus `SLATE_TERM_SERVICE_ID`, `SLATE_TERM_SERVICE_GENERATION`, `SLATE_TERM_SERVICE_PLUGIN_ID`, `SLATE_TERM_SERVICE_TOKEN`. The CLI uses these only as handshake credentials, not claimed provenance. Partial/malformed service context fails before connecting and never falls back to the administrative socket. Explicit cross-app/administrative routing must not silently drop a service identity.
- Ordinary native/admin commands, panel servers and terminal children must not inherit a service credential accidentally. However, a host-launched service-owned command is an intentional delegated descendant: supply its owner's authenticated endpoint/credential rather than the normal administrative connection, after revalidating that owner. Retain a separate host-stamped service owner through A→CLI→B nesting; every descendant request uses the service adapter and admission. Its command-plugin ID/launch settings may differ from its service authority; never derive authority from `SLATE_TERM_PLUGIN_ID` or an invocation ID. Intentional descendants can inherit the bearer credential: this is bearer authentication for trusted same-user controllers, not a process sandbox or defense against that service sharing its credential.
- Host status/events/diagnostics never insert the credential. Raw service stdout/stderr may contain secrets printed by the service and are administrative-only. No credential persistence, manifest field, argument, event payload or discovery listing.

## Exposure, targeting and causation

Service requests use a distinct authenticated adapter, not the administrative handler with an environment label.

- Same bridge-equivalent exposure policy as registered pages, rechecked at dispatch including indirect `command.run`: shared inspection/layout/tab operations, structured web actions, terminal control, custom events, own settings and contributed commands. No plugin registration, global configuration writes, native-window administration, screenshot/filesystem output, arbitrary browser evaluation, or service administration.
- No implicit pane belongs to a service. Per-view operations carry explicit targets, frozen and revalidated across awaits. Genuinely app-scoped reads/actions remain unanchored; do not manufacture page/session context. Document any deliberate active-context fallback rather than inheriting the page adapter's self-targeting assumption.
- Add a typed service origin and a separate service-generation causation audience. Public origin contains bounded plugin/runtime/generation identity; private roots/references remain host-owned. Page and service references are not interchangeable; restart retires references for that generation.
- Per-plugin admission combines its page and service activity, with the existing global bucket/depth rules. Readiness and emergency stop/disable cannot be trapped behind a mutator's exhausted budget. Ordinary service mutations do not acquire administrative or native exemptions.
- Accepted work retains its admitted lineage; completion facts do not revalidate an expired cause. Actual later submissions/input claims still validate the live caller generation.

## Readiness, snapshots and events

- After spawn the service is `starting`. Only authenticated `service.ready({version:1})` transitions that current generation to `ready`; duplicate readiness is idempotent, foreign/retired readiness is rejected. Failure to acknowledge within the bounded manifest timeout stops that generation and follows restart policy.
- Before ready, permit readiness, discovery and read/resnapshot methods only; deny mutations. Bootstrap order is fixed: obtain a workspace snapshot and retain its INITIAL event cursor across all pages; then fetch current own settings; then acknowledge readiness and poll from that retained cursor. Repeat the whole synchronization on snapshot conflict or expired history. A change between those reads is therefore still in retained history; replayed settings notices are invalidations/refetches, not external-action jobs. This is an explicit service-author obligation, not a claim that the host can prove arbitrary external state is synchronized.
- Process environment/settings JSON is a launch snapshot. A ready service fetches current own settings explicitly. Directed settings notifications include version1, public source/applied revisions and bounded value-free changed paths; never foreign namespace values. Both starting and ready authenticated generations must be eligible recipients: a settings change between bootstrap fetch and ready acknowledgement must remain replayable from the retained snapshot cursor, even though pre-ready polling is forbidden.
- Extend journal recipient matching with an explicit `targetService:{serviceId,generation}` target, distinct from `targetInstanceId`; reject publications specifying both. Service filter serialization uses `serviceRecipient`, with null/ambiguous recipient forms rejected. This is host-selected routing, not a new caller-supplied authority or automatic expansion of `events.emit` parameters. Administrative observers retain visibility; unrelated pages/services never receive another service's directed facts. Use an explicit observer audience (administrator/page/service generation), rather than treating a missing page recipient as administrative. Apply that audience on every match and generation retirement check. The journal cursor remains an epoch/sequence position, not an authorization credential; do not add an authenticated cursor store. Do not impersonate a logical page instance to reuse its filter.
- Event delivery issues generation-bound causation references using the existing retention/reservation rules. Global settings envelopes stay opaque even for services.
- Expired cursor/app epoch returns the existing resync error. Example/SDK repeats the snapshot-FIRST algorithm above, then subscribes from the retained initial cursor. It never silently skips history or replays external actions. Registration has no event-based activation rules.

## State, persistence and restart policy

States: `disabled`, `stopped`, `starting`, `ready`, `backoff`, `failed`, `stopping`. Status separately reports enabled-on-start intent, generation, bounded failure/restart metadata and process state; user intent is not inferred from running state. Accepted administrative lifecycle intents are host-owned: requester disconnect does not roll back an accepted start/restart or abandon cleanup. Reject cancellation before admission; subsequent stop/disable/remove/shutdown supersedes pending launch intent. This differs intentionally from service-owned in-flight requests/jobs, which retire with their generation.

- `start`: explicit current-session launch, without enabling future startup. Already starting/ready/backoff is idempotent and does not replenish or shortcut retries. Start during stopping conflicts before effects. A new explicit start from disabled/stopped/failed resets the restart budget without changing persisted opt-in.
- `stop`: retire the generation and stop it now, without clearing persisted startup intent. A stopped service does not immediately restart itself merely because enabled remains true.
- `restart`: stop and explicitly start a fresh generation/reset budget. Concurrent restarts share the same retiring resource cleanup; only the latest accepted lifecycle intent may launch a successor.
- `enable`: persist user opt-in, then start if needed, and activate on later app startup. `disable`: persist opt-out, then retire/stop. Persist failure must not report a successful preference change or tear down an otherwise live generation.
- Persist enabled IDs in the same atomic PluginCatalog snapshot as registrations (schema2, read schema1 as no enabled services). Register/replace clears opt-in for that ID; unregister removes it in the same write. This avoids a failed second preference-file write resurrecting opt-in for a newly registered plugin. Replacement retires the old service only after successful catalog persistence.
- At most 16 enabled services and 16 active process generations app-wide; capacity preflight precedes persistence/spawn or supersession. Backoff reservations count toward the active bound. No eviction to make room.
- Use a per-registration lifecycle intent nonce, separate from process generation. Capture it before cleanup awaits and revalidate intent, registration revision and registration existence immediately before successor launch. Stop invalidates older start/restart intent; successful disable/remove/replace persistence invalidates it before yielding. A superseded call returns observed status with `superseded:true`, not a claim that its earlier stop was rolled back. Keep the capacity reservation through cleanup and transfer it to a successor rather than double-counting or releasing early. Repeated enable of a starting/ready/backoff service is idempotent; enable during stopping conflicts before persistence. Persisted opt-in remains explicit in results when a subsequent spawn fails.
- Automatic activation happens only after host configuration, catalog, journal and workspace restoration are ready, rechecking current opt-in/registration at each launch (not just when collecting the startup list). Wire startup activation only after explicit-start ownership/causation/resync tests pass.
- Reuse restartLimit 0…10; bounded exponential delays 1/2/4/8 seconds. Readiness success does not replenish the budget, so flapping cannot restart forever. Explicit restart/start resets it. Every attempt has fresh endpoint/credential/generation. Stop, disable, unregister and shutdown cancel backoff/readiness tasks before cleanup.
- Status/list are bounded by catalog 64 entries; logs use existing 64KiB tails per stream, from only the current/last run per registration. No unbounded generation history or accumulated output. Failure facts carry enums/bounded public identity, not arguments, environment, output or arbitrary diagnostics.

## Owned work and teardown ordering

Retire admission/credentials first; close peers to cancel pending requests; cancel specifically owned contributed-command jobs and await bounded group cleanup; stop the service's own supervised group; publish final observed state. A generation retains its own teardown resource capsule until cleanup finishes, never overwritten by its successor.

- Stamp service owner identity separately from causation: ownership is not inferred from a shared root or matching plugin ID. A service may invoke another plugin's command; stopping it cancels that owned invocation, not unrelated invocations or the other plugin's panel/service.
- Event polls, browser waits and pending terminal claims are cancelled. Terminal input already released and JS/clicks already submitted cannot be undone. Retired generation validation prevents a pending terminal claim or delayed new web submission from taking effect; outstanding WebKit platform slots retain their existing lifetime rules.
- Process exit/timeout also retires outstanding requests/jobs before restart. App shutdown closes services before the event journal. Host SIGKILL relies on the existing worker watchdog. Descendants that deliberately daemonize out of the owned group remain an explicitly documented limitation, not contained processes.
- Preflight/publish bounded `host.service.state.changed` before starting external effects. Later observed transitions publish at current revisions using the admitted context (or a distinct host lifecycle context for autonomous exits/restarts). Files/processes/journal are not one rollbackable transaction; late publication failure must not fabricate process rollback or authorize replay.

## Required focused verification

Headless first: strict manifests/service-only compatibility, catalog v1→v2 and atomic failure behavior, collision with contributed `plugin.service.start`, token/generation/hello bypass negatives, default admin handshake unchanged, CLI poisoned/partial context, exposure and indirect denial, recipient isolation and cursor binding, shared admission/causation audiences, restart caps/timeouts and stop-during-backoff.

Owned native process fixture without windows: ready protocol, start/stop/restart, timeout/exit, parent death, descendant cleanup, log bounds, retired credentials, late terminal claim and nested command ownership (including a different plugin's command). Real-host integration must later verify settings notifications/resync, disable/unregister/shutdown, independent panel/command lifetimes and automatic startup only after opt-in. Those runtime checks are not replaced by a successful compile.

## Bounded review disposition

The read-only reviewer found five design/integration hazards, not an implemented runtime defect: (1) nested command connections would revert to the existing administrative socket; (2) settings-first bootstrap could lose notifications; (3) restart could outlive concurrent disable/unregister; (4) protocol/decode errors could bypass repeated-hello revocation; (5) pre-ready polls/idle peers could starve readiness. The contract now specifies delegated authenticated routing, snapshot-first synchronization, lifecycle intent revalidation/reservation transfer, pre-validation revocation plus malformed-peer close, and bounded peer/poll lifetimes. Tests must reproduce each hazard before claiming the runtime complete.

Keep one typed observer audience instead of optional recipient fields with implicit administrator semantics. Reuse settings-error sanitization for services. No new cursor-token store, process launcher or generic workflow engine is justified.
