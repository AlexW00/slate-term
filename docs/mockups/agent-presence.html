Mockup v2 agent presence

Frame and tag, nothing else.

When an agent touches a pane, Slate highlights the smallest target it knows about: the exact element if possible, otherwise the whole pane. A tag says who is acting and why. Tags show for a minimum time, stay while the work is actually running, and fade once the agent is done. The demo below walks through six cases. Click a chapter to jump to it.

      01 how long a tag stays

      Minimum hold, then follow the work.

      Most agent calls finish in milliseconds, which is too short to see. Some run for seconds or minutes. The tag's lifetime tracks the real operation, with a floor so short calls stay readable.

      0s1s2s3s4s5s6s
      Instant callterminal capture · 40 ms
      hold 1.6sfade
      Repeat within holdsame agent, same target
      merged, hold extends, note swapsfade
      Running operationterminal run · 4.2 s
      live: spinner + elapsed timeresultfade
      Leasepresence hold … release
      held until release, or TTL with no callsfade
      • Floor of about 1.6 s. Long enough to read "claude · reading test output" once, short enough not to linger. It fades over 0.5 s instead of disappearing abruptly.
      • Real duration when there is one. terminal run, terminal wait, web wait and navigation already have deadlines in the API. The tag shows a spinner and elapsed time until they settle, then a short ✓ or ✕.
      • Leases for "I'm working here". presence hold keeps the tag up across many short calls. Any call from that agent to that pane refreshes it. A TTL (default 60 s) clears it if the agent crashes, so tags never go stale.
      • No resting state. Once an agent is done, the pane looks exactly like it did before. Nothing marks where an agent lives.

      02 where the tag goes

      Anchored to the header, or to the element.

      A pane tag hangs from the bottom edge of the pane header at the top right, like a tab attached to the frame. An element tag sits on the element's own frame, top left. Both are overlays: anything that takes a row of layout space would change a terminal's size.

      Chosen

      Header bottom edge

      Reads as part of the frame. It covers a small corner of content that is usually empty in terminals, and the header itself stays untouched. The same tag style is used on element frames.

      Rejected

      Inside the header

      Competes with the pane title, the type menu and plugin header controls. Narrow panes have no room, and two or three agents push into the title.

      Rejected

      Bottom overlay / own line

      As an overlay it sits on the prompt, where the user and the agent type. As a separate line it resizes the terminal each time an agent shows up, so full-screen programs like vim or Claude Code would reflow.

      03 smallest known target

      Frame the element, not the pane, when we can.

      The pane frame is the fallback. Each canonical web.* action already resolves a selector or ref to one element, and snapshots report element rectangles. That works for browser panes and registered plugin pages, so plugins get element frames without writing code.

      04 several agents, one pane

      Stack, then compress.

      • One frame, shared. With one agent the ring is its color. With several, the ring becomes a gradient through their colors in arrival order. No second ring and no flicker between colors.
      • Stable order. The first tag sits in the corner and later ones line up to its left. Tags never reshuffle. Each leaves on its own timer.
      • Color per agent type. Known agents keep one color, so orange always means Claude. Unknown names get a stable hashed color from a palette that avoids the known colors and the red/green used for results.
      • Suffix only when ambiguous. With one Claude active the tag says claude. With two at once, each gains its home pane from SLATE_TERM_PANE_ID: claude · p1, claude · p7.
      • Compress at three. From three tags up, everyone except the newest collapses to just the name. The group stays narrow and the latest "why" is still readable.
      • A new action pulses, it doesn't replay. A call to an already-framed pane brightens the glow once. That's the "something happened" signal from the website, without restarting the entrance animation.

      05 API

      An env var, an optional flag, and a value-free event.

      Every typed CLI command already sends through one connection object, so actor support is one change in the CLI plus the host. Nothing is required from agents: a call without an actor shows no presence, which keeps humans and scripts unaffected.

      # once per agent session; the Slate skill or the
# agent's own setup exports it
export SLATE_TERM_ACTOR=claude

# optional on any command
slate-term terminal capture --pane p2 \
  --note "reading failing test output"

# optional lease for multi-step work
slate-term presence hold --pane p4 --ttl 60s \
  --note "triaging the sprint board"
slate-term presence release --pane p4

# read current presence (names + notes)
slate-term presence list --tab t1 --json

# on the wire: request metadata, next to "cause"
"metadata":{"version":1,
  "actor":{"name":"claude","note":"reading failing test output"}}
      • Optional, not required. A required flag would break people, scripts and every agent that doesn't know about it. SLATE_TERM_ACTOR names the agent once; --note adds the why per call.
      • Metadata, not params. The actor rides in the request metadata next to cause, so every command gets it without new arguments. Host decoding is strict today, so this needs a new api.describe capability. The CLI only sends the actor to hosts that advertise it.
      • Agents only. Calls without SLATE_TERM_ACTOR show nothing: plain scripts, shell tools, plugin pages and services, with no guessing from process names. An agent that runs a plugin command through the CLI still shows as that agent.
      • One switch. Settings → AI Agents → Show agent activity on panes (agents.show_activity) hides it all. Also in ⌘K, command run agents.activity.toggle and slate-term agent-activity hide.
      • Display only. The actor is self-declared and never affects admission or authorization. That is also why reading it from the environment is acceptable, unlike cause.
      # host.presence.changed, published on transitions only
{"topic":"host.presence.changed",
 "tab":"t1","pane":"p5",
 "payload":{
   "activityId":"a42", "phase":"began",
   "actionKind":"wait",
   "actor":{"name":"gemini","claimed":true},
   "origin":"administrative",
   "target":{"pane":"p5"}}}

# later: phase "ended", result "ok", count 1
      • A subscribable event, but value-free. Existing host.* events never carry free text such as titles or notification bodies. The event says who started or stopped what, where. The note lives in presence list, like titles and notifications.
      • Transitions, not calls. The journal keeps 1,024 events. An agent polling capture ten times a second would push everything else out within a minute. One began when an activity starts and one ended after it goes idle, with a call count, keeps it bounded.
      • No feedback loops. Reads aren't rate-limited, so a subscriber that reacts to presence with a read could loop. Calls that carry a cause don't create presence. Presence is also rate-limited per actor.
      • Plugin elements get a directed copy. When the target is an element in a plugin page, the owning page also receives the event, so it can react in its own UI.

      06 feasibility

      Mostly existing patterns.

      PieceEffortWhat already exists
      Pane frame + tagEasyPaneInactiveShade and PaneDropPreview already paint over Metal and WebKit content with hitTest returning nil. Presence is one more sibling view on top, so layout and terminal size don't change.
      Presence state + timersEasyA transient per-pane dictionary beside leaves/containers in WorkspaceHost, pushed to pane chrome the way notification indicators are.
      Begin/end for every callEasy–moderatedispatchAPI is the single path for CLI, plugin and service calls. Every handler is awaited, so wrapping it gives real durations for run, wait and navigate.
      Actor in requestsModerateOne Connection.request for all CLI commands. Needs the metadata key, capability negotiation and docs.
      Element framesModerateclick/fill/select already compute getBoundingClientRect and scroll the element into view. They need to return it. Snapshots already report rects. Wait needs a rect added.
      Event + presence listModerateJournal, routing and directed delivery exist. The new parts are transition coalescing and the per-actor rate limit.

      Risks: element frames go stale if the page scrolls or navigates, so keep them short-lived. Glows must stay inside the pane bounds or neighbours clip them. Pane replacement and zoom must keep the overlay on top. Very narrow panes need a name-only tag.

      Mockup only. Scripted, not wired to the app. The presence logic in the script (hold floor, merging, leases, crowding) follows the rules above.
